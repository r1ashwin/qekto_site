Product

One control plane for every model call

Qekto sits between your application and your model providers. You get full visibility into your AI traffic from day one. Repetitive workloads graduate to models you own, but only when the evidence supports it.

Proxy

Change one line, keep your semantics

Model, messages, tools, tool choice, structured output options, temperature and token limits pass through untouched. Upstream status codes and error bodies are returned exactly as the provider sent them.

EndpointBehavior
POST /v1/chat/completionsStreaming and non-streaming. Text, image_url, input_audio and file parts plus tool calls are analysed into typed metadata. Eligible requests can be served by an owned model.
POST /v1/responsesPass-through (streaming and non-streaming), with typed metadata.
POST /v1/embeddingsPass-through. Vectors are never stored.
GET /v1/modelsYour provider's model list.
Audio, image and file endpointsRejected with a precise 501 endpoint_not_supported before any upload is read, so Qekto never silently alters payloads it cannot handle.

Retries happen only when a request provably never reached the provider. Timeouts and unreachable providers map to clear 504 and 502 errors. If analytics fail, traffic keeps flowing.

Multimodal data plane

Typed content, not flattened strings

Each request is recorded as a typed envelope: modality, MIME type, size, SHA-256 and an object reference for every part, kept separately from request metadata.

By default Qekto stores metadata and PII-redacted text only. Full text and raw media storage are per-project opt-ins. Base64 media never enters the database. Qekto never fetches URLs found in payloads.

Workload contracts

Qekto learns how you use AI

Onboarding captures your product, users, compliance constraints, modalities, latency and cost goals, success criteria, available ground truth and training rights.

Each detected workload gets a versioned contract covering task family, input and output schema, evaluator and thresholds, SLOs, privacy, and rollout policy. Unknown task families are still captured and routed to your provider.

Graduation

Capability matching, not wishful thinking

Plugins for trainers, evaluators and serving runtimes declare what they support. Qekto picks candidates from the workload contract. If nothing fits, it explains what is missing.

Evaluation and release

A release is a pull request for a model

Frozen, stratified holdout

Holdout assignment is deterministic and persisted, and stratified by label for classification workloads. An input never moves between train and holdout.

Three-way comparison

The candidate is scored against the active owned model and against your provider's captured answers on the same holdout, with per-slice scores and case-by-case diffs.

Release cards

JSON and Markdown cards record the gate decision, regressions, dataset provenance, training-rights attestation and artifact hash.

Shadow

A candidate runs on live traffic after your provider answers. Agreement is measured and the candidate never serves.

Canary and auto-rollback

The candidate serves a configurable share of traffic. It is promoted or rolled back automatically from observed fallback rate, and invalid or low-confidence outputs fall back to your provider.

Kill switch

One setting or one CLI command forces all of a project's traffic back to your provider on the next request.

Control plane

Dashboard and CLI

The dashboard shows traffic, workloads, latency, tokens, estimated cost, errors, fallback rate, model versions, release cards, jobs with logs, and the audit trail. Every number comes from your own traffic.

Everything critical is also scriptable from the CLI.

qekto workloads --project P
qekto graduate  --project P --workload W --wait
qekto release   --project P --version-id V
qekto promote   --project P --workload W --version-id V --mode canary
qekto rollback  --project P --workload W --reason "incident 42"
qekto force-upstream --project P --on
qekto audit     --project P --workload W
